# Проверка персональных данных на изолированном PostgreSQL

Команда подготовки (без изменений БД): `pnpm check:personal-data:db`.
После согласования миграций: `pnpm check:personal-data:db --run`.

С браузерным E2E: `pnpm check:personal-data:db --run --browser`.
Используется установленный Playwright Chromium; для локального Edge в PowerShell
задайте `$env:E2E_BROWSER_CHANNEL='msedge'`. Браузер не устанавливается автоматически.
Режим запускает настоящий API и Vite на отдельных loopback-портах, создаёт
синтетического администратора и секретаря. Рабочие `.env` не загружаются ни
API, ни Vite, ни помощником авторизации. Уже работающие серверы не переиспользуются.
Playwright останавливает созданные серверы, runner затем останавливает Postgres.

Нужны установленные PostgreSQL 16, Node и зависимости workspace, собранный
`@streetlifting/domain` и актуальный Prisma client API. Установка зависимостей
и генерация клиента не выполняются этим скриптом автоматически.
В Windows используется `C:/Program Files/PostgreSQL/16/bin`; другой путь можно
передать через `PG_BIN`. В Linux укажите каталог с `initdb` и `pg_ctl`.

## Изоляция

Скрипт создаёт новый каталог `output/personal-data-db/run-*`, отдельный кластер
Postgres на свободном loopback-порту и случайный пароль. Две БД имеют имена
`streetlifting_e2e_fresh` и `streetlifting_e2e_upgrade`. Он не подключается
к уже работающему Postgres и не принимает внешний DATABASE_URL.

Дочерние процессы получают только системные переменные и синтетические настройки
этого запуска. Проверка не загружает рабочие `.env`, использует локальное файловое
хранилище и Fastify inject с настоящими middleware, JWT, Prisma и транзакциями.
Рабочие данные, внешние сервисы и production не затрагиваются.

## Что проверяется

1. Полная цепочка миграций на пустой БД.
2. Обновление с состояния перед миграцией
   `20260919020000_pd_operator_and_access_acknowledgment`: существующая роль
   сохраняется, подтверждение не проставляется автоматически.
3. Регистрация без организатора и с устаревшим текстом не создаёт спортсмена.
4. Два одновременных запроса регистрации дают одну заявку; сохраняются точные
   тексты, версии и scope согласий, отсутствует невыбранное согласие результатов.
5. Подтверждение роли проверяет владельца и версию, активирует исходный scope;
   повтор не меняет первоначальную дату и не создаёт второй аудит.
6. Реальная загрузка и чтение PNG; закрытие публичной выдачи по scope/hidden;
   запрет обхода через вложения; немедленный отзыв роли и согласия через API.
7. Создание вложения паспорта, заявки, удостоверения, разряда и внешней привязки:
   реальные записи и UUID в аудите совпадают. Повторный upsert сохраняет ID
   привязки и не создаёт дубль; обе записи аудита ссылаются на этот ID.
   Непривилегированный пользователь не может выдавать удостоверения/разряды
   или подтверждать внешнюю привязку.

При успехе создаётся `result.json`. В `finally` останавливается только созданный
кластер; каталоги и синтетические данные сохраняются для диагностики. Скрипт
не выполняет reset/drop и не удаляет файлы.

Это интеграционная проверка API и БД. Она не заменяет браузерный E2E с настоящим
сервером, schema drift check, проверку ISF ID или подтверждение production.

Опция `--browser` дополнительно проверяет принятие допуска через интерфейс,
публичную регистрацию и приватный просмотр загруженного фото при отсутствии
согласия на его публикацию. Эти сценарии не используют моки API. Отчёт браузера
сохраняется в `browser.json` рядом с `result.json`; `browser: true` в итоговом
результате появляется только после успешного завершения браузерных тестов.

В CI сценарий включён перед браузерными тестами в job `e2e` на отдельной БД
`streetlifting_e2e_ci`. Путь upgrade проверяет локальный runner. Изменение workflow
не является свидетельством успешного запуска GitHub Actions.
