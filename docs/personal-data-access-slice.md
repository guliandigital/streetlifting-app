# Согласия и допуск представителей федерации

Локальный срез от 19 сентября 2026 года. Продолжение незакоммиченной работы Claude
в `claude/project-analysis-2c13f0`. Это описание поведения программы, а не
подтверждение юридического соответствия или готовности production.

## Реализованное поведение

- В настройках федерации сохраняются название, адрес, контакт оператора ПД и
  HTTP(S)-ссылка на политику. Действуют существующие права администратора федерации
  и аудит изменений. При незаполненных реквизитах используются название и контакт
  федерации; такое состояние не означает готовность юридических документов.
- Публичная регистрация получает тексты от сервера и передаёт
  `consentSnapshotHash` (SHA-256 показанных текстов, версии и языка). Если текст,
  оператор или организатор изменился после открытия формы, сервер возвращает
  `409 consent_changed` до создания заявки. Форма обновляет тексты и сбрасывает
  галочки. В `consent.textShown` сохраняется именно принятый текст, отдельные
  согласия на результаты и фото создаются только при выборе пользователя.
- Для `federation_admin`, `secretary`, `accountant`, `head_judge`, `judge`,
  `scoreboard_operator`, `speaker` роль не участвует в авторизации до принятия
  текущей версии обязательства. Scope роли остаётся прежним. Администратор
  платформы сохраняет доступ для администрирования и восстановления.
- `/auth/me` возвращает `pendingAcknowledgments`; GET
  `/auth/access-acknowledgment` — текст, POST
  `/auth/role-assignments/:id/acknowledge` — принятие своей неотозванной роли.
  Повторное принятие текущей версии не перезаписывает первоначальное свидетельство.
  Изменение роли во время подтверждения даёт 409; новая версия требует принятия заново.
- До принятия интерфейс показывает обязательство вместо содержимого рабочего
  раздела. Ошибку загрузки можно повторить; выход из аккаунта доступен в оболочке.
- Онлайн-регистрация и переход турнира в `in_progress` требуют подтверждённого
  участника команды с ролью `organizer`. Участник связан с аккаунтом пользователя;
  приватные контакты команды не публикуются в ответе регистрации.

## Порядок выпуска

1. Миграция `20260919020000_pd_operator_and_access_acknowledgment` проверена на
   изолированной локальной БД с нуля и поверх предыдущей схемы
   ([результат](personal-data-db-check.md)). К рабочим БД не применялась.
2. Обновить API и web согласованно: POST публичной регистрации теперь требует
   `consentSnapshotHash` из GET регистрации. Старый клиент без поля получит 400.
3. До запуска обеспечить администраторам доступ к подтверждению, заполнить
   реквизиты федераций и подтвердить организаторов действующих турниров.
   Ранее выданные затронутые роли также потребуют подтверждения; автоматического
   принятия или массового заполнения свидетельств нет.
4. Проверить на тестовой БД полный путь: сохранение настроек → показ согласий →
   регистрация → запись текста; выдача роли → принятие → отзыв; запуск турнира.

## Границы

Локальная проверка: `pnpm lint`, `pnpm typecheck`, `pnpm test`, сборки api/web/isf-id,
`typecheck:e2e` и `git diff --check` прошли. API: 91 тест. Два новых браузерных
сценария прошли в установленном Edge с полностью замоканным API. Обе Prisma-схемы
валидны; для ISF ID использован фиктивный URL локальной БД без подключения.
Стандартный `release:check` первоначально остановился на отсутствии его
`DATABASE_URL`, оставшиеся этапы выполнены отдельно. Полный E2E с реальной БД
и применение миграций не выполнялись.

Срез не переносит БД/файлы и не меняет DNS. Он не реализует интерфейс выдачи ролей,
сбор согласий на мандатной комиссии, согласия представителей несовершеннолетних,
экспорт/анонимизацию, сроки хранения, очистку, S3 и ограничения публикации фото.
Эти пункты общего аудита остаются отдельными задачами. Тексты согласий и модель
ответственности требуют отдельной правовой проверки; наличие полей и галочек
не подтверждает заключение договоров или выполнение внешних процедур.
